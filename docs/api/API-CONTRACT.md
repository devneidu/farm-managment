# Farm Management API — V1 Contract

The frontend-facing contract of the finished V1 backend. It was written by auditing the running code (routes, FormRequests, resources, enums, services, feature tests) and was verified by **executing every documented request against the real application** and by a live HTTP session check of the Sanctum flow. Where the older docs, the blueprint (`docs/implementations/`) or the OpenAPI file disagree with the code, this document describes the code and the disagreement is listed in [`docs/postman/COVERAGE.md`](../postman/COVERAGE.md).

* Reference with every endpoint, field list, example and saved response: the Postman collection `docs/postman/Farm-Management-API.postman_collection.json`.
* How to *use* the API from React: [`FRONTEND-INTEGRATION.md`](FRONTEND-INTEGRATION.md).
* Executable end-to-end flows: [`docs/postman/WORKFLOWS.md`](../postman/WORKFLOWS.md).
* Machine-readable spec: `docs/api/openapi.json` (generated by Scramble; see the discrepancy list).

Phase 20 (WhatsApp / AI parsing) is deferred and is **not** part of V1: no such endpoint exists.

## 1. Base API

| Item | Value |
|---|---|
| Prefix / version | `/api/v1` (all application endpoints; there is no unversioned API) |
| Local base URL | `http://localhost:8000/api/v1` with `php artisan serve` (WAMP: `http://localhost/<site>/public/api/v1`). Postman variable `base_url` includes `/api/v1`. |
| Staging / production | Use one `base_url` per environment, for example `https://api.<staging-domain>/api/v1` and `https://api.<domain>/api/v1`. The SPA and API must be under the same registrable domain (cookies are `SameSite=Lax`): `app.<domain>` + `api.<domain>` with `SESSION_DOMAIN=.<domain>` and `SESSION_SECURE_COOKIE=true`. |
| Request headers | `Accept: application/json` always. `Content-Type: application/json` for bodies; `multipart/form-data` (field `file`) for record attachments. |
| Browser headers | The browser adds `Origin` and cookies; with `fetch` use `credentials: 'include'`, with Axios `withCredentials: true` and `withXSRFToken: true`. |
| Request id | Every response has `X-Request-Id` (also exposed to CORS). Errors echo it as `request_id`. A client may send its own `X-Request-Id` (8-64 characters of `A-Za-z0-9._-`) and the API reuses it; otherwise a UUIDv7 is generated. Log it with every error report. |
| Other response headers | `Cache-Control: no-store, private`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Language`, `Vary: Accept-Language, Origin`. |
| Locale of messages | English only in V1. Branch on `code`, never on `message` (messages may be localised later). |

`GET /health` (public) returns `{"data": {"status": "ok", "service": ..., "version": ..., "timestamp": ...}}`.

## 2. Authentication

Authentication is **Laravel Sanctum first-party SPA cookie authentication**. The session lives in an HttpOnly cookie (named after the app, `farm_management_api_session` locally - never hard-code the name; `SameSite=Lax`, 120-minute lifetime by default). **No endpoint issues bearer/API tokens in V1**: do not build a token flow, never store credentials in `localStorage`.

### 2.1 How the SPA session actually works (verified over real HTTP)

1. `GET /auth/csrf-cookie` → `204`, sets two cookies: the HttpOnly session cookie and a **readable** `XSRF-TOKEN` cookie.
2. Every **POST / PUT / PATCH / DELETE** must send the cookie's value, URL-decoded, in the header `X-XSRF-TOKEN`. (Axios does this automatically; with `fetch` read `document.cookie`, `decodeURIComponent` it, and set the header.) Missing/stale token → `419 session_expired`: call the csrf endpoint again and retry once.
3. **Every request must carry an `Origin` (or `Referer`) from a stateful frontend domain** — listed in the backend `SANCTUM_STATEFUL_DOMAINS` (host:port, no scheme; local defaults `localhost:3000`, `localhost:5173`) and in `CORS_ALLOWED_ORIGINS` (with scheme). Browsers add it. Two consequences verified live:
   * `POST /auth/register` without an `Origin` → `400 stateful_request_required` (no account is created).
   * An existing session cookie **without** a stateful `Origin` is not honoured: `GET /auth/me` answers `401`. So a Postman/cURL client must add the `Origin` header on *every* request (the Postman collection does it automatically: visible `Origin` / `X-XSRF-TOKEN` headers filled by its pre-request script from the cookie jar).
4. CORS: allowed origins come from `CORS_ALLOWED_ORIGINS`, `Access-Control-Allow-Credentials: true`; `X-Request-Id` is exposed. A disallowed origin gets no CORS headers.
5. Cookies are `SameSite=Lax`; in production use HTTPS with `SESSION_SECURE_COOKIE=true`.

Unauthenticated protected request: `401` `{"code": "unauthenticated"}`. Suspended account: `403 account_suspended` (and the session is ended).

### 2.2 Endpoints

| Flow | Method + URL | Auth | Body | Result |
|---|---|---|---|---|
| CSRF init | `GET /auth/csrf-cookie` | public | – | `204`, cookies |
| Register | `POST /auth/register` | public | `email`, `password`, `password_confirmation` | `201` auth state (`next_action: verify_email`), user logged in, OTP emailed |
| Verify email (OTP) | `POST /auth/email/verify` | session | `code` (6 digits) | `200` auth state (`complete_farm_setup`) |
| Resend OTP | `POST /auth/email/resend` | session | – | `200 {cooldown_seconds}`; during the 60 s cooldown `429` + `Retry-After` |
| Login | `POST /auth/login` | public | `email`, `password` | `200` auth state; `401 invalid_credentials` (same for unknown email and wrong password) |
| Logout | `POST /auth/logout` | session | – | `200`; ends this browser session only |
| Forgot password | `POST /auth/password/forgot` | public | `email` | always `200` (no account enumeration); emails a 6-digit code |
| Verify reset code | `POST /auth/password/verify-otp` | public | `email`, `code` | `200 {reset_token, expires_in}` |
| Reset password | `POST /auth/password/reset` | public | `email`, `reset_token`, `password`, `password_confirmation` | `200`; does NOT log in; all sessions revoked |
| Google | `POST /auth/google` | public | `credential` (Google ID token) | `201` new / `200` existing account; `401 invalid_google_credential`; `503 google_unavailable` when `GOOGLE_CLIENT_ID` is not configured |
| Current user | `GET /auth/me` | session | – | `200` auth state; `401` = show login |
| Onboarding | `POST /onboarding/farm` | verified | `name` | `201` auth state (`next_action: none`) |
| Accept invitation | `POST /invitations/accept` | verified | `token` | `200` auth state + `meta.accepted_farm_id` |

Rules worth knowing:

* **OTP**: 6 digits, expires after 10 minutes, single use, invalidated after 5 wrong attempts; verification failures are always the same `422` with `errors.code` ("The code is invalid or has expired."). `resend` has a 60 s cooldown and is limited to 5/hour.
* **Password rules**: 8-72 characters, at least one letter and one number, confirmation must match.
* **Reset**: `reset_token` is single use and valid 15 minutes (`expires_in: 900`). Unknown email, wrong/expired/used code all produce the same `422`.
* **Google**: the email is treated as verified and no OTP is sent; an existing email/password account with the same email is linked, not duplicated. Success cannot be reproduced without a real Google ID token; the failure shape is saved in the collection.
* **Local OTP/invitation emails**: with `MAIL_MAILER=log` they are written to `storage/logs/laravel.log`.
* **Rate limits** are per endpoint (see §15). `429` carries `Retry-After`.

### 2.3 Account suspension

A platform admin can suspend a user (`POST /platform-admin/users/{user}/suspend`). From then on every authenticated request of that user is `403 account_suspended` and their session is ended; `POST /auth/login` is `403 account_suspended`. Memberships and farm data are untouched; `…/restore` reverses it.

## 3. Auth state and `next_action`

`register`, `login`, `google`, `email/verify`, `onboarding/farm`, `invitations/accept` and `GET /auth/me` all return the same object:

```json
{
  "data": {
    "authenticated": true,
    "email_verified": true,
    "onboarded": false,
    "has_active_farm": false,
    "next_action": "complete_farm_setup",
    "user": {
      "id": "01a1045e-3bbd-71f5-b8b6-0aa8ede5c0b5",
      "email": "ada.okafor@example.com",
      "name": null,
      "email_verified_at": "2026-10-04T00:45:08+00:00",
      "has_password": true,
      "platform_role": null,
      "providers": [],
      "locale": null
    },
    "farm": null,
    "farms": [],
    "marketplace": {"shop_count": 0}
  },
  "meta": {},
  "message": null
}
```

A user with a farm returns, for example, `"farm": {"id": "…", "name": "Okafor Integrated Farms", "country_code": "NG", "currency": "NGN", "timezone": "Africa/Lagos", "locale": "en", "role": "owner"}` and `"farms": [{"id": "…", "name": "Okafor Integrated Farms", "role": "owner"}]`.

| Field | Meaning |
|---|---|
| `authenticated` | always `true` in this payload |
| `email_verified` | email OTP completed (or Google) |
| `onboarded` | the user has completed farm setup **once**; never cleared, even if every membership is later removed |
| `has_active_farm` | the user has at least one ACTIVE membership; `data.farm` is the default one (oldest active membership) or `null` |
| `next_action` | the **only** thing routing should read |
| `user.platform_role` | `admin`, `support` or `null` — shows the Platform Admin area (a different system, §14) |
| `user.providers` | linked social providers (`["google"]`) |
| `farm.role` | the caller's role id on the default farm. **Permissions are not here** (see §5). |
| `marketplace.shop_count` | Marketplace shops the user is a member of (any status; Phase 22). Independent of farms: a user can have farms, shops, both or neither |
| `farms[]` | every farm the user ACTIVELY belongs to, `{id, name, role}`, oldest membership first (the first one is the default `farm`). Empty when there is no active membership. Removed memberships never appear. It is the discovery list for `X-Farm-Id` (§4); it carries no permissions and no farm settings. |

`next_action` values (computed in this order; `marketplace` sits between `verify_email` and `complete_farm_setup` and applies only to farm-less shop members):

| `next_action` | Condition | Frontend should |
|---|---|---|
| `verify_email` | email not verified | show the OTP screen (`/auth/email/verify`, `/auth/email/resend`). The user is logged in but every farm endpoint answers `403 email_verification_required`. |
| `complete_farm_setup` | verified, never onboarded | show the farm-name screen → `POST /onboarding/farm`. Farm endpoints answer `403 onboarding_required`. (An invited user skips this: accepting an invitation marks them onboarded.) |
| `no_active_farm` | verified, onboarded, but no active membership (removed from their last farm) | show a "you have no farm" screen. They are **not** sent back to setup (`POST /onboarding/farm` is `409 already_onboarded`); farm endpoints answer `403 no_active_farm`. Accepting a new invitation brings them back. |
| `marketplace` | verified, **no active farm**, but a member of at least one Marketplace shop (`marketplace.shop_count > 0`); returned instead of `complete_farm_setup` / `no_active_farm` for that user only | show the seller area (`GET /marketplace/my/shops`). Farm endpoints still answer `403 onboarding_required` / `no_active_farm`; offer "Set up a farm" (`POST /onboarding/farm`, still allowed) as an optional extra. Never returned to a user with an active farm |
| `none` | normal access | load the app (`GET /farm`, `GET /dashboard`, …) |

Saved responses for each state are in the collection folder **01 — Authentication** (after OTP: `complete_farm_setup`; after being removed from the only farm: `no_active_farm`).

## 4. Farm context

* Farm-scoped endpoints **never take a farm id** in the URL, query or body (sending `farm_id` is rejected with `422`). The API resolves the farm from the caller's own **active memberships**.
* **Default**: the caller's oldest active membership.
* **`X-Farm-Id: <farm uuid>`** (optional request header) selects another farm the caller **actively** belongs to. It can never grant access: any other value is `403 farm_access_denied`.
* No active membership: `403 no_active_farm` (or `403 onboarding_required` if the user never set up a farm).
* **Discovering farms (multi-farm V1):** `GET /auth/me → data.farms[]` (`{id, name, role}`, active memberships only). Plans may limit how many farms a user can hold (Free = 1) while paid users may belong to several. There is **no "switch farm" endpoint**: the existing header is authoritative. To change farm: send the chosen `farms[].id` as `X-Farm-Id` → `GET /farm` (membership + permissions of that farm) → `GET /subscription/entitlements` → clear/refetch farm-scoped data. Refetch `/auth/me` after accepting an invitation (`meta.accepted_farm_id`) or losing a membership.
* **Membership removal**: the member loses access immediately (their next request is `403 no_active_farm` / `farm_access_denied`); records they created remain.
* **Isolation**: every farm-owned resource is scoped server-side. An id that exists in another farm is `404 not_found` — never `403` — so existence is not disclosed.
* Platform Admin routes have no farm context at all.

## 5. Roles and permissions

### 5.1 What the frontend receives

| Source | Gives |
|---|---|
| `GET /auth/me` → `farm.role`, `farms[].role` | the role **id** only (of the default farm / of each listed farm). No permissions. |
| `GET /farm` → `membership` | `id`, `role`, `role_label` and the **complete `permissions` list** (strings) of the caller on the current farm. **This is the source of truth for showing/hiding UI.** |
| `GET /roles` (needs `team.view`) | the five role presets with their `permissions` and, per role, `assignable` (may the caller assign it?) — for the invite / change-role dialogs |
| `GET /subscription/entitlements` (any role) | plan features/limits (a separate system, §5.4) |
| permissions endpoint | **none**: there is no `GET /permissions` in V1 |

Show an action when `membership.permissions` contains the permission the endpoint requires (listed in every request description as "Required backend farm permission"). **The frontend never sends a permission string**; the backend re-checks every request (`403 forbidden` if missing).

### 5.2 Roles (presets)

`owner`, `manager`, `farm_worker`, `finance`, `vet` (labels: Owner, Manager, Farm Worker, Finance, Vet).

* The **Owner** gets every permission. An Owner may invite/assign `manager`, `farm_worker`, `finance`, `vet`. A **Manager** may invite/assign/remove only `farm_worker`, `finance`, `vet`.
* **Nobody can assign `owner`** (`422 ownership_transfer_unsupported`), change their own role, or demote/remove the last owner (`409 last_owner`). Hierarchy violations are `403 insufficient_role`.
* Invitations: `POST /farm/invitations {email, role}`; the token is emailed (7 days, single use) and never returned. The invitee registers/logs in with the **same email** and calls `POST /invitations/accept {token}`.

### 5.4 RBAC vs entitlements

A request needs both: **RBAC** (does the user's role have the permission? → `403 forbidden`) and **entitlements** (does the farm's plan allow it? → `403 feature_not_available`, `403 subscription_inactive`, `409 plan_limit_reached` with `details {entitlement_key, limit, usage, remaining}`). Check order: authenticated → active membership → RBAC → entitlement → business validation. Current entitlement keys: features `advanced_reports`, `data_export`; limits `team_members`, `active_cycles`. Never hard-code plan names or limits: read `GET /subscription/entitlements`.

### 5.5 Platform Admin authorization (separate)

Platform roles `admin` (read + write) and `support` (read only) are granted only by an operator (`php artisan platform:grant-admin`), appear as `user.platform_role` in the auth state, and authorise only `/platform-admin/*`. Farm roles confer nothing there and platform roles confer nothing on farm routes. See §14.

## 6. Identifiers

**Every public resource is identified by a UUIDv7 string.** There are no integer ids anywhere in the API. Never construct, sort or parse ids. Human-readable `reference` codes are display strings, not identity; stable machine `code`s identify catalogue data.

| Resource | Public identifier | Example | Notes |
|---|---|---|---|
| User | UUIDv7 `id` | `01a10412-73c1-73f6-bf29-d93b2bb51cbe` | `data.user.id` |

## 8. Pagination, filtering, search

* **Pagination**: `page` (≥ 1) and `per_page` (1-100; reports 1-500). Envelope `meta: {current_page, per_page, last_page, total}`. Defaults differ per endpoint (table below). Small, complete collections are **not** paginated and return the full array with `meta: {}`: `/public/plans`, `/roles`, `/farm/members`, `/farm/invitations`, every `/master/*` list (operations, species, breeds, crops, varieties, dimensions, units, location types, record types, health record types, task categories), `/custom-breeds`, `/custom-varieties`, `/settings/measurement-contexts`, `/settings/package-conversions`, `/work-templates` (+ `/recommended`), `/breeding-projects/{id}/milestones`, `/calendar`, `/finance/categories`, `/reports`, and the Platform Admin capability/settings/feature-flag lists. `/insights` returns `meta.total` and `by_severity` instead of page counters.
* **Search**: farm endpoints use `search` (case-insensitive substring; some also match references); Platform Admin endpoints use `q`.
* **Sorting**: there is no `sort` parameter on farm endpoints; each list has a fixed order (newest first for ledgers/records, name for places/contacts). Platform farms list accepts `sort` (`name`|`created_at`) and `direction`.
* **Date ranges**: ledgers and documents use `from` / `to` (inclusive **farm-local** days, `YYYY-MM-DD`) — finance, purchases, sales, invoices, payments, reports, audit, calendar. Records, health records and inventory movements use `recorded_from` / `recorded_to`. Tasks filter the due date with `from` / `to`. Reports also take `as_of`.
* **Filters** are plain query parameters named after the field (`status`, `kind`, `production_cycle_id`, `contact_id`, `type`, …); every request description in the collection lists the ones that exist, with allowed values.
* **Booleans in query strings**: send `1` / `0`. Laravel's `boolean` rule rejects the strings `true`/`false` on most endpoints (verified: `include_inactive=true` → `422`). The master-data lists additionally accept `true`/`false`.
* Unknown query keys are ignored; invalid values are `422`.

## 9. Idempotency

Mutations that record a real-world event take a client-generated **`idempotency_key` in the JSON body** (not a header). 1-80 characters of letters, digits, `.`, `_`, `:`, `-`; tasks, schedules, template applications and report exports require at least 8. Generate one UUID per user action; reuse it only to retry that same action.

* **Same key + same payload** → the original result again (status `201` for creations, `200` for an export), with **no second side effect** (no second stock movement, expense, population change, …).
* **Same key + different payload** → `409 idempotency_conflict`.
* A failed attempt does not consume the key.
* Scope: farm-wide for events, per user and farm for exports.
* Not idempotent by key (no key accepted): plain CRUD such as places, contacts, custom breeds, measurement settings, feed formulas, inventory items, cycles (names are unique instead), invitations.

## 10. Dates and time

* **Timestamps** are UTC ISO-8601 (`2026-10-04T00:01:58.000000Z` or `…+00:00` depending on the resource; parse them with a real date parser, never by string slicing).
* **`recorded_at`** is when an event really happened. It is **kept separately from `created_at`** (when the system stored it). On every write endpoint that takes it, send `YYYY-MM-DDTHH:MM:SS` followed by `Z` or `±HH:MM` — **no fractional seconds** (`2026-10-04T08:30:00+01:00` ✔, `2026-10-04T07:30:00.000Z` ✘). It must lie between the cycle start (farm-local midnight) and now.
* **Farm-local dates** (`start_date`, `planting_date`, `due_date`, `occurred_on`, `received_on`, `from`, `to`, `as_of`, …) are calendar days `YYYY-MM-DD` interpreted in the farm timezone (`Africa/Lagos` by default; returned in `farm.timezone`). 23:30 UTC on the 14th is already the 15th in Lagos.
* **Due dates**: tasks have farm-local `due_date` + optional `due_time`; `due_at` is the UTC instant after which an open task is overdue; `due_state` is derived (`upcoming`, `due_today`, `overdue`, `completed`, `cancelled`). A task with no time is due by the end of its day.
* **Dashboards and reports** compute "today", "last 7 days", "this month" and report ranges in farm-local days; the response says which day it used (`farm.today`, `meta.today`, `timezone`).
* **Biological expected dates** (breeding) and `expected_end_date` are references/estimates, not guarantees.

## 11. Money

* Amounts are **decimal strings with at most two decimals** (`"1500.50"`), positive, at most 16 integer digits (`^\d{1,16}(\.\d{1,2})?$`). Integers and JSON numbers with ≤ 2 decimals are accepted on input, but **send strings**. No thousands separators, no negatives, no more than two decimals (`"10.555"` → `422`).
* The API computes totals with exact decimal arithmetic and always returns two decimals: a purchase of `9000.00 + 1250.45` is `"10250.45"`, a sale of `27000.00 + 60000.00` is `"87000.00"`. **Do not recompute authoritative totals in JavaScript floating point**; display the returned strings, and if you must add, use a decimal library or integer minor units on your own side.
* Currency is the farm's (`NGN`) and is never client-supplied.
* Plan prices are **integer minor units** (`amount_minor: 300000` kobo = ₦3,000.00) with a display-only `formatted`.
* Reports return money as two-decimal strings and quantities as strings.
* Cash basis: **income is booked when a payment is received**, never when a sale or invoice is created (§17).

## 12. Measurements

* Every quantity belongs to a **dimension**: `weight`, `volume`, `area`, `count`, `temperature`, `package`. `GET /master/measurement-dimensions` lists them with the canonical unit; `GET /master/units?dimension=…` lists the units of ONE dimension (never load all units). Send unit **codes** (`kg`, `l`, `hectare`, `crate`).
* **Canonical units** (stored, normalised): grams `g`, millilitres `ml`, square metres `sq_m`, pieces `piece`/`egg`/`head` (separate count families), `celsius`. **Display units** are the farm's `GET /settings/units` preference; they never change stored values.
* **Quantities are exact decimal strings** (≤ 12 integer and ≤ 6 fractional digits); discrete units (head, egg, piece) reject fractions; only temperature may be negative.
* **Compound quantities**: `components: [{quantity, unit}, …]` (1-10 parts), e.g. `12 bag + 18 kg`. The response keeps `entered` (what the user typed), `normalized` (canonical) and `total`, plus a replayable `snapshot` of the conversion used.
* **Package conversions are contextual**: a `bag` has no universal size. It converts only inside a context given by `(context_type, context_id)`: `crop_type` (a crop id), `custom` (a farm measurement context id) or `inventory_item` (an inventory item id). Feed "bag = 25 kg" and maize "bag = 50 kg" coexist. Without the context: `422 conversion_context_required` / `ambiguous_conversion`; no definition: `422 conversion_not_configured`. Inventory stock movements resolve packages only through the item's own conversion.
* **Live preview**: `POST /measurements/normalize` returns the exact result the save would produce (example: 3 crates + 14 pieces in the "Eggs" context where 1 crate = 30 pieces → `104 piece`; 12 bags + 18 kg of a 25 kg/bag feed item → `318 kg`).
* Planting units, land area and planting-material quantity are three **separate** measurements (800 heaps ≠ 800 tubers ≠ 2 hectares).

## 14. Platform Admin (separate from farm roles)

* Base `/api/v1/platform-admin`, **no farm context**, no `X-Farm-Id`, no farm permissions.
* Access: a `platform_admins` grant created only by `php artisan platform:grant-admin {email} --role=admin|support` (revoke: `platform:revoke-admin`). No API can create or escalate a grant.
* Roles: `admin` read + write; `support` read only (`403 platform_write_forbidden` on writes). No grant: `403 platform_admin_required`.
* Middleware: authenticated → active → verified → platform grant; writes also rate limited (60/min).
* **A farm Owner/Manager has no access here, and a platform admin has no farm powers** (an admin without a membership gets `403` from `/farm`). Platform Admin never edits a farm's operational data.
* Capabilities: plans/prices/entitlements and moving a farm to a plan, system reference data and species capabilities, platform work templates (draft → published → archived), settings (`support_email`, `support_whatsapp`, `announcement`), feature flags, users (search, suspend, restore), farms (search, support overview), platform audit trail. No DELETE anywhere.
* `GET /auth/me` → `user.platform_role` tells the frontend whether to show the admin area; `GET /platform-admin/me` returns `{user, role, can_write}`.

## 17. Domain concepts the API enforces

Verified against the implementation (and exercised by the workflows):

* **Livestock population is derived.** `initial_population` is the immutable starting count; `current_population` = the sum of the population ledger (mortality −, births +, reconciliations ±, livestock sales −, reversals). There is no endpoint to set it. Example from the workflows: 500 initial − 5 deaths − 2 reconciliation = 493; +37 hatched = 530; −12 sold = 518.
* **Crop planting units vs material vs area**: `initial_planting_units` (heaps/holes/stands) is the baseline for planting/establishment/loss; seed/tuber quantity is recorded only on planting records (`components` + stock link); land `area` is a separate optional measurement.
* **Task = should happen; record = did happen.** Tasks, schedules and templates never create operational/health records, stock movements or finance entries; completing a task can only link an already-saved record as evidence.
* **Append-only corrections.** There is no PATCH/DELETE on records, health records, movements, finance transactions, sales, payments. Correct with **reverse/cancel** (a new row with the opposite effect) and, where offered, a replacement carrying `corrects_*_id`. Original rows stay readable with `reversed_by_*` links.
* **Inventory balance is derived from movements.** No endpoint writes a balance; stock can never go negative, not even at a past `recorded_at`. Manual stock-in/out, adjustments, transfers; movements created by a record, health event, purchase or sale are reversed through that parent.
* **Package conversions are contextual** (§12).
* **Biological expected dates are references** (exact date or window, never a midpoint), not guarantees.
* **Sale, invoice and payment are three separate concepts.** A sale records what left the farm (stock-out and/or livestock exit) and books no income; an invoice is the customer document snapshotted from the sale; a **payment is what books income** (one payment = one income ledger row). `sale.payment_status`: `uninvoiced` → `unpaid` → `partially_paid` → `paid`.
* **Eggs, milk and feed: one event, one entry** ([FEED-EGGS-MILK-STOCK.md](FEED-EGGS-MILK-STOCK.md)). `egg_collection` / `milk` records write a stock-in (reason `production`) on the farm's automatic Eggs / Milk item in the same transaction; `feed_use` with `details.inventory` writes the stock-out (`production_use`); a breeding project with `consume_egg_stock` writes the `incubation` stock-out; sales write the `sale` stock-out. Donated/purchased/received stock is `POST /inventory/stock-in` and never a production record. **Available balance = SUM of movements; production totals are a separate figure.** Reasons that another workflow owns are `422` on the manual endpoints; `GET /master/inventory-options` returns labels and the authoritative route per action.\n* **Stock lines can name the output instead of an item** (`items[].output: "eggs"|"milk"` on `POST /sales` and `POST /purchases`; exactly one of `output` / `inventory_item_id`). A purchase resolves or creates the farm's output item and receiving store like `stock-in {output}`; a sale takes the existing item only (never creates stock; `409 insufficient_stock` otherwise).
* **A stocked purchase is the one path that writes stock and money together** (one `stock_in` per stock line + one expense), atomically. Finance transactions never touch stock.
* **Platform Admin is not Farm Owner** (§14).
* **Marketplace listings** ([PHASE-23-MARKETPLACE-LISTINGS.md](PHASE-23-MARKETPLACE-LISTINGS.md)): money and quantities are decimal strings (NGN, `amount_minor` in kobo); package contents are seller-declared and never a conversion; a listing is public only while `published` AND its shop is `active` (evaluated on read); publishing/linking inventory never moves stock; the public quantity is `seller_declared`; an image is optional (placeholder indicator); catalogue images are illustrative.
* **Marketplace offers & purchase intents** ([PHASE-24-MARKETPLACE-OFFERS.md](PHASE-24-MARKETPLACE-OFFERS.md)): controlled negotiation on negotiable listings, not chat/escrow/checkout. An offer is a unit price strictly below the listed price and not below `marketplace_min_offer_percent` (default 70%) of it, with a quantity; max `marketplace_max_offers_per_buyer` (3) per listing (voided offers refunded), one open at a time, expiry `marketplace_offer_expiry_hours` (48h) enforced on read and write; the shop's owner/manager (`offer.respond`) accepts or rejects; accepted = immutable agreement in principle (no stock reserved, no sale, **no seller contact** until Phase 25). "Proceed at listed price" is an idempotent purchase intent (interest only). New shop permissions `offer.view` (all roles), `offer.respond` (owner, manager). New 409 codes: `listing_not_negotiable`, `offer_pending`, `offer_limit_reached`, `offer_already_accepted`, `offer_expired`, `offer_voided`, `offer_not_pending`, `listing_unavailable`; new 403 code `cannot_negotiate_own_listing`.
* **Marketplace deals** ([PHASE-25-MARKETPLACE-DEALS.md](PHASE-25-MARKETPLACE-DEALS.md)): a deal is a frozen **summary** of terms both sides agreed, not an order, invoice, payment, escrow or delivery - Farmvest collects no payment, holds no funds, reserves or deducts no stock and posts no Sale/finance record. Two doors, two yeses: (A) the **buyer** confirms an offer the seller accepted, within `marketplace_deal_confirmation_hours` (72h) of acceptance; (B) the seller (`deal.respond`) confirms a fixed-price purchase request (no agreement, no contact), then the **buyer** confirms those exact terms. Idempotent, DB-unique per source. Frozen `terms` (`product_total` covers the product only); `fulfilment.method` is `pickup` or `seller_delivery`; `delivery_charge.amount` is `null` ("To be agreed directly") unless the seller proposed a figure the buyer confirmed, and is never added to the total. Completion is **self-reported by both sides** (`completion.verification: self_reported`), never automatic; either party can cancel an active deal (contact access ends; shared details cannot be recalled); reports (any state) never change the deal and are hidden from the other party. Contact only through `GET …/deals/{deal}/contact` (buyer gets the shop's channels, address only for pickup; seller gets name + email + optional per-deal phone), audited, rate-limited, never in any other payload. Admins: read-only deals, reports and audited contact.
* **Marketplace monetisation** ([PHASE-26-MARKETPLACE-MONETISATION.md](PHASE-26-MARKETPLACE-MONETISATION.md)): Farmvest's own service fees only (seller plans per shop, promoted listings), paid through Paystack; never buyer-seller payments, commission, escrow, wallets or payouts. Money is a naira decimal string (`"5000.00"`), always `NGN`. A checkout creates a `pending` payment with a frozen price and an `authorization_url`; **nothing is activated by the redirect, the client or the webhook body** - only by server-side confirmation from Paystack of the exact reference, amount and currency (`POST .../payments/{reference}/verify` and the signed webhook are both idempotent). Publishing beyond the plan limit is `409 listing_limit_reached` (existing listings are never deleted or paused); an expired plan reads as Free at read time. Public listings carry `promotion: {label: "Sponsored"} | null` - always display it. New shop permissions `billing.view|manage` (owner, manager); new codes `monetisation_disabled`, `plan_not_purchasable`, `subscription_active`, `package_not_available`, `listing_not_promotable`, `promotion_active`, `payments_unavailable`, `gateway_unavailable`, `invalid_signature`.

## Phase 27 — Marketplace trust, safety and administration

See [the complete Phase 27 contract](PHASE-27-MARKETPLACE-SAFETY.md). Existing shop approval, verification, suspension and listing restriction are reused. New participant APIs file shop/listing complaints and list/read owned content or deal reports. New platform APIs provide `/platform-admin/marketplace/summary`, read-only `/offers[/{offer}]`, and `/reports[/{type}/{report}[/transition]]`. Report states are `open -> in_review -> dismissed|resolved`; every handling action requires a reason. A report never enforces automatically. Only explicit `enforcement_action` plus the related target UUID can invoke existing suspension/restriction. All report counts are available by status, including zeros. Read permissions remain platform admin/support, writes admin only.

**Frontend contract changes:** reinstatement and lifting listing restrictions now require `{reason}`. Active duplicate reports use reporter + target + issue; a closed case permits a new report. Intake throttling is shared across content/deal reports, 20/hour/user. Show own complaint/outcome privately; internal history and reporter identities belong only in the platform administration area. Existing deals, stock and financial records are preserved; paid periods are not extended or refunded by enforcement.
